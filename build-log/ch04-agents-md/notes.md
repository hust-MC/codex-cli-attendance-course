# 第四章录课讲解点

## 本节主线

第三章的 Prompt 很长，因为规范只能塞在 Prompt 里。这一节把规范搬进 `AGENTS.md`，然后用一条短 Prompt 干活，对比效果。

## 建议录制顺序

1. 回顾第三章的 Prompt，问观众：这段话里哪几句和请假加班没关系？（大部分都没关系）
2. 打开 `AGENTS.md`，说明这些句子被搬到了哪里。
3. 现场跑一遍规范与代码的一致性核对，把 `consistency-check.md` 里那 6 处不一致摊开讲。
4. 用 `course/prompts/ch04/codex.md` 里的短 Prompt 干活，展示它自动遵守了注释、错误码、目录分层。
5. 对比 DeepSeek 版：同样的需求，规范只能粘进 Prompt 里，任务描述反而更短。

## 可以强调的工程点

- **规范要跟着代码一起维护**：不是写完就完，字段名改了规范要跟着改。
- **判断标准是长期稳定性**：字段名是实现细节，改规范更省；「还没做到哪」是状态，该标注不该删。
- **不同工具的规则承载方式不同**：Codex 放文件，DeepSeek 放 Prompt，效果一样，成本不同。
- **Prompt 的长度不由需求复杂度决定**，由你有没有把规则沉淀在别处决定。

## 本节真实状态

- 本轮没有运行时 Bug。
- 真实收获是 6 处规范漂移，其中 `overtimes` 字段名（规范写 `date`、代码是 `work_date`）和 JS 封装函数名（规范写 `api_request()`、代码是 `request()`）都是最容易被观众记住的例子。
- 还有一处硬伤：规范里写着「每个可运行阶段保持一次清晰提交」，但工作区根本不是 Git 仓库。这条留到讲 Git 快照时再补。

## 录课时可以抛给学生的问题

- 规范里该不该写「请假冲突只和已审批记录比较」这种业务规则？
- 如果规范写了「列表返回 total 和 items」，AI 写错的时候你能一眼看出来吗？
