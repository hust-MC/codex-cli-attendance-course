# AGENTS.md 与短 Prompt 对比

## 这一节要讲什么

同一个项目里，技术栈、目录职责、接口格式、数据库规则和测试要求是长期稳定的。它们不应该在每一轮任务中重复声明。

`AGENTS.md` 负责保存稳定规则，任务 Prompt 只负责本轮增量。这样录课时可以直观展示：

- 没有项目规范时，Prompt 越写越长，而且容易漏掉约束。
- 有项目规范时，Prompt 可以非常短，AI 仍然能按同一套工程标准工作。
- 真正需要现场表达的是本轮需求，而不是每次重复“请加中文注释”。

## 不使用 AGENTS.md 时的 Prompt

下面是一份“示意版”长 Prompt。它把项目背景和固定规范全部塞进单轮任务，实际录制时容易占满屏幕，也不利于长期维护。

```text
请继续开发指尖打卡 2.0 项目，本轮实现请假和加班模块。

项目使用 Python 3.10、Flask 3、SQLite 和原生 JavaScript，不能引入 ORM，
不能修改 requirements.txt 中已有依赖的版本，默认数据库是 checkin.db，
测试时通过 CHECKIN_DB_PATH 切换数据库。

代码必须加中文注释，Python 函数名用 snake_case，类名用 PascalCase，
每行不能超过 120 个字符，JavaScript 不能使用 var，只能使用 const 和 let。

路由放在 routes/，业务逻辑放在 services/，模型放在 models/，
路由层不能直接写 SQL，所有数据库访问必须经过 service 层。

接口统一返回 {"code": 200, "message": "...", "data": ...}，
参数错误返回 400，资源不存在返回 404，服务器错误返回 500。
列表接口返回 total 和 items，不要返回裸数组。

请假类型只能是事假、病假、年假、调休，开始日期不能晚于结束日期，
请假审批只能从 pending 变成 approved 或 rejected，已审批记录不能重复处理。
加班时长必须大于 0 且不超过 24 小时，审批状态同样只能从 pending 流转。

所有接口都要使用参数化 SQL，写操作必须 commit，异常要回滚，
不能吞异常，不能留下调试输出，不能修改员工和打卡模块的已有行为。

请为请假和加班补充 unittest 测试，测试使用临时数据库，
覆盖正常流程、参数错误、重复审批和状态非法流转。
完成后运行 python3 -m unittest discover -s tests -v 和 bash scripts/verify.sh，
并把真实 Prompt、命令、测试输出、错误记录和结果写入 build-log/ch03-leaves-overtimes/。

本轮不实现考勤日核算、异常生成、申诉和月报。
```

### 这种写法的问题

- 固定规范占据大量篇幅，真正重要的本轮需求反而不突出。
- 每次都要复制，漏掉一条就会导致生成风格不一致。
- 项目规则变化后，需要修改所有历史 Prompt，无法统一维护。
- 录制时观众看到的是“背诵规范”，不是“如何提出有效需求”。

## 使用 AGENTS.md 后的 Prompt

项目根目录已经提供 `AGENTS.md`，上面这份长 Prompt 中的技术栈、目录、编码、API、数据库和测试规则都不需要重复。

下面这份是准备在第三章开工时实际使用的短 Prompt：

```text
请阅读并遵守根目录 AGENTS.md。

本轮实现请假与加班模块：
1. 请假支持新增、列表、详情、审批通过和驳回。
2. 加班支持新增、列表、详情、审批通过和驳回。
3. 校验日期范围、请假冲突、加班时长、员工状态和审批状态流转。
4. 补充 tests/test_leaves.py、tests/test_overtimes.py，并运行完整测试。
5. 更新首页入口，保证可以从页面完成一次申请和审批。
6. 将真实 Prompt、命令、测试输出和结果写入 build-log/ch03-leaves-overtimes/。

本轮不实现日考勤核算、异常生成、申诉和月报。
```

### 为什么这样就够了

- `AGENTS.md` 已经定义技术栈、目录分层、响应格式和测试要求。
- Prompt 只说明本轮新增业务、验收动作和明确不做的范围。
- 如果实现偏离规范，评审时可以直接引用 `AGENTS.md` 的具体章节。
- 讲解重点从“重复规则”转向“如何拆分一个可验收的业务阶段”。

## 稳定性与可变性划分

| 内容 | 放在哪里 | 原因 |
|---|---|---|
| 技术栈、目录职责 | `AGENTS.md` | 整个项目周期稳定 |
| 编码风格、注释要求 | `AGENTS.md` | 每个文件都要遵守 |
| API 响应格式、错误码 | `AGENTS.md` | 所有模块共享 |
| 数据库路径和核心约束 | `AGENTS.md` | 跨模块长期有效 |
| 考勤、请假、加班规则 | `AGENTS.md` | 业务规则需要统一 |
| 测试和开发记录要求 | `AGENTS.md` | 每个阶段都要执行 |
| 本轮要做的接口 | 任务 Prompt | 每个阶段变化 |
| 本轮验收场景 | 任务 Prompt | 需要现场演示 |
| 本轮明确不做的内容 | 任务 Prompt | 防止范围扩散 |
| 临时排障信息 | 对话或修复 Prompt | 只对当前问题有效 |

## 录课演示建议

1. 先展示长 Prompt，让观众看到重复声明的成本。
2. 打开根目录 `AGENTS.md`，快速定位目录规范、API 规范、测试规范和完成定义。
3. 再展示短 Prompt，强调它只描述本轮增量。
4. 用同一句提问做对比：“如果没有 AGENTS.md，AI 怎么知道错误码怎么返回？”
5. 最后说明：`AGENTS.md` 不是一次写完就永远不动，项目规则变化时要同步维护。

## 录制时的关键话术

> Prompt 不是越长越专业。稳定的工程约束应该沉淀到项目规范里，任务 Prompt 只负责说清楚这一轮要交付什么。

> 如果每一轮都重复声明同一批规则，说明这些规则应该进入 AGENTS.md，而不是继续堆在 Prompt 里。

> AGENTS.md 的价值不是让 AI “记住一句话”，而是让代码、测试、接口和文档使用同一套验收标准。

## 注意事项

- 不要把“当前做到第几步”“今天的临时决定”写进 `AGENTS.md`，这些属于阶段记录。
- 不要把未确认的设想写成硬性规范，否则后续开发会被错误约束。
- `AGENTS.md` 中的规则必须能对应到真实代码或测试，不能只写口号。
- 规则发生变化时，先更新规范，再更新任务 Prompt 和阶段记录。
