# 第五章 · DeepSeek 版

> DeepSeek 读不到仓库文件，所以这段 Prompt 必须把业务规则和已知 Bug 都写进去。
> 这正好说明了第四章的结论：规范放不进文件，就只能贴进 Prompt。

## Prompt 一：写一个能复现 Bug 的测试

```text
你是一位 Python 测试工程师。下面是我的项目结构和一个已知 Bug，
请帮我写一个能稳定复现这个 Bug 的 unittest 用例。

项目结构：
- app.py：Flask 入口
- db.py：SQLite 连接和建表
- services/leave_service.py：请假业务逻辑
- services/errors.py：ServiceError 异常，code 默认 400
- tests/base.py：测试基类 DatabaseTestCase，提供 self.create_employee()、
  self.create_leave() 等辅助方法

已知 Bug：
员工可以提交两条时间重叠的请假申请。提交时因为两条都是 pending 状态，
所以都不会触发冲突校验。主管先审批通过第一条，再审批通过第二条时，
系统也没有重新检查冲突，导致数据库里出现两条时间重叠的已审批请假。

正确的行为应该是：审批通过之前重新检查一次，
如果和已有的已审批请假时间区间重叠，应该抛出 ServiceError，
错误信息里要包含「冲突」两个字。

要求：
1. 用 Python 标准库 unittest，不要 pytest。
2. 直接给出完整测试文件内容，标注文件名。
3. 测试要断言到具体的错误信息，不要只断言异常类型。
4. 不要修改任何业务代码。

先说明一下你打算怎么复现这个 Bug，然后给出代码。
```

## Prompt 二：分析并修复

```text
接着上一轮。测试已经能复现这个 Bug 了。

现在请你：
1. 解释冲突校验当前在哪个函数里，为什么这个场景能绕过它。
2. 给出最小修复方案，说明改哪个函数、加什么判断。
3. 给出修复后的完整函数代码。
4. 补充两个边界情况的测试：
   - 驳回后重新提交同一时间段应该还能通过
   - 与已审批请假不重叠的申请应该能正常审批通过

按「先解释、后给代码」的顺序回答。
```

## 录课时注意

- 第一段 Prompt 长度是第五章 Codex 版的 4 倍，多出来的全是「本该在 AGENTS.md 里」的内容。
- 同一个 Bug，两个版本的成本差在这里：Codex 读文件，DeepSeek 靠你粘贴。
- 第二段让模型「先解释后给代码」，对 DeepSeek 尤其重要，它容易一上来就吐代码。

## 已知会踩的坑

- DeepSeek 容易在解释里编造函数名，代码给出来才发现对不上。
- 它可能把冲突检查加在提交时而不是审批时，修复不到根因。
- 一定要要求它给出「完整的修复后函数」，否则你得自己拼上下文。
