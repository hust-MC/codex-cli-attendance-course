# 第五章 · Codex CLI 版

> 第五章讲的是「用测试约束 AI 开发」。
> 这条 Prompt 是本轮主线：一次性把测试基础设施和全部单元测试写出来。

## Prompt 一：建立测试基础设施

```text
在当前 Flask 项目里建立单元测试基础设施。

要求：
1. 创建 tests/ 目录，文件命名为 test_*.py。
2. 用 Python 标准库 unittest，不引入 pytest。
3. 测试必须使用临时数据库，通过 CHECKIN_DB_PATH 环境变量隔离，
   绝对不能污染根目录的 checkin.db。
4. 每个测试用例开始前清空业务数据，保证用例之间互不影响。
5. 提供公共基类，封装建员工、建打卡、建请假、建加班的辅助方法，
   避免每个测试重复写插入语句。
6. 测试文件必须有中文 docstring，说清这个用例在验证什么。

只做基础设施，先不要写具体测试用例。
```

## Prompt 二：补齐四个模块的单元测试

```text
现在补齐单元测试，覆盖已有代码的所有业务分支。

范围：
- 员工：新增、重复工号、必填校验、超长校验、列表筛选（关键字/部门/状态）、
  修改、逻辑离职、重复离职。
- 打卡：签到、签出、重复签到、未签到先签出、离职员工打卡、
  非法员工编号、非法打卡类型、带 location 和 remark 签到、记录查询。
- 请假：提交、天数计算、非法类型、日期格式、开始晚于结束、
  与已审批请假冲突、审批通过、重复审批、驳回、通过后不能再驳回。
- 加班：提交、时长为 0、超过 24 小时、非数字、同日重复、
  审批通过、重复审批、驳回。

要求：
- 每个分支至少一个用例，正常流程和错误流程都要覆盖。
- 断言要具体，不要只断言「不报错」。
- 跑通全部测试后再交付，把测试数量和结果告诉我。

本轮不修改业务代码，只写测试。如果发现业务代码有 Bug，
写一个能复现它的失败测试，然后停下来告诉我，不要自己改实现。
```

## Prompt 三：只解释不修改（分析 Bug）

```text
现在有一个失败测试：

test_approve_leave_conflict_with_approved_blocked
AssertionError: ServiceError not raised

场景是：员工提交了两条时间重叠的请假，两条都是 pending 状态。
主管先审批通过第一条，再审批第二条时，系统没有报冲突错误。

请只分析，不要修改任何代码：
1. 读一下 leave_service.py，说明冲突校验当前是在哪个函数里做的。
2. 说明为什么这个场景能绕过校验。
3. 说明修复应该放在哪一层、需要改哪几个函数。
4. 列出你判断的依据和对应的代码行号。

不要写实现代码，先把原因讲清楚。
```

## Prompt 四：最小修复

```text
按你的分析做最小修复。

要求：
1. 只改必要的函数，不要重构无关代码。
2. 修复后失败的测试必须变绿。
3. 跑一遍全部测试，确认没有引入回归。
4. 把修复前后的差异贴给我看。

不要额外加新功能，也不要顺手改测试的断言。
```

## Prompt 五：回归评审

```text
最后做一次回归评审：
1. 跑全部测试，把结果贴给我。
2. 检查这次修复有没有遗漏的边界情况：
   驳回后再提交同一时间段还能不能通过？
   与已审批请假不重叠的申请还能不能正常审批？
   非工作日请假会不会被误判成冲突？
3. 如果发现遗漏，先写失败测试再告诉我。

不要修改实现代码，只做检查和补测试。
```

## 录课时注意

- Prompt 二结尾那句「不要自己改实现」是重点：它演示了 TDD 的核心纪律。
- Prompt 三「只解释不修改」也是重点：先理解再动手，能避免大部分返工。
- 这个 Bug 是真实存在的，不是编的。修复过程就是从红到绿。

## 已知会踩的坑

- 模型很容易在写测试时顺手改业务代码，Prompt 二和四都要明确禁止。
- 它可能给每个测试方法都复制一遍建员工的 SQL，Prompt 一的公共基类能挡住。
- 临时数据库用完不清理会在项目根目录留下 `test_checkin.db`，提醒它删掉。
